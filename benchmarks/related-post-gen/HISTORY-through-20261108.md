It recommends five related posts by counting shared tags. Compiler changes use the same verified Mech source; separately named source experiments test loop and representation changes. The headline ratio measures **a complete fresh process from launch through exit**, including all setup, program loading, allocation, JSON IO, computation and cleanup, divided by the fastest verified external complete process; smaller is faster. A secondary continuous post-JSON interval includes native input admission, intervening allocation and worker creation/run/join. Preinitialized worker pools and prepared-input timers do not qualify for that secondary comparison. Historical reports retain their original policy and timer boundaries. Standard Rust remains the output oracle and a secondary timing reference. The original M1 baseline and newer same-machine M3 comparisons are separate. [compiler-work.json](results/compiler-work.json) records compiler fixes and remaining measured costs.

`related.mec` performs string tag indexing, inverted-index construction, shared-tag counting, stable top-five selection, counter clearing, and output-index allocation. `runner.rs` is a Rust host adapter for JSON, native snapshot admission, invocation, and JSON output. This measures an embedded native Mech program; it is not a standalone, submission-ready implementation of the upstream benchmark's JSON interface.

## Runtime diagnosis and further lowering

The Rust and Mech implementations both build inverted posting lists. On the exact 5,000-post input, the source-derived work is **18,161,514 posting increments**, with 28 distinct tags. Mech scans padded counters in 64-lane chunks, causing **395,000 child-loop activations**. These counts explain the workload; the large slowdown comes from the cost of executing it. A non-timed allocation diagnostic at 500 posts counted 2,442,322 requests and 407,405,249 requested bytes. Requests scaled roughly with tag occurrences across 100/500/1,000 posts, rather than with chunk activations. There was no evidence for the initially suspected whole-counter copy on every chunk. [Diagnostic methods, counts and limitations](results/runtime-gap-diagnosis/diagnosis.json) distinguish observations from hypotheses.

Four further compiler changes target the actual profile without changing `related.mec`:

- Parent numeric segments use prepared physical scalar bindings. Generated code loads current scalar payloads and publishes successful outputs directly; it no longer walks aggregate paths or zeroes all scratch words. Adjacent admission and numeric entry share one callback, with the original logical admission and error order.
- Child numeric loops import only the carrier leaves, fuel and exact array views they need. The hot ranking loop imports 13 scalars, copies zero shadow argument words on entry, and keeps 28 private boundary words instead of the former 224 scratch words. Successful scalar publication follows checked managed-owner reconciliation; cold errors, finite-fuel exits and first-write boundaries retain the original reification and charges.
- Retained Map ownership supports flat Tuple/Record results containing exactly one `Map<String,u64>` and scalar U64 fields. This selects the native membership path at the actual `RelatedIntern` site 54. Shared Engine constructor-cost functions preserve original-site output/clone limits, including shape-normalization costs. Record alias tracking declines private ownership where an older Map version escapes; bounded optional-proof exhaustion falls back to canonical storage.

- A compiler-proved borrowed view connects a published Record's constant Map field to one adjacent read-only Map operation. The canonical Record remains the owner. Exact arena-generation/visit witnesses fit existing metadata slack, with no child Map Value, draft, persistent cache or pointer retained. Both original admission boundaries and logical caps remain. Unsupported uses and owner-declined paths use both ordinary calls. The derived proof is serialized, explicitly hashed and rechecked when loading (**IR152/work104/ABI38**). [Engine cap/error tests](results/compiler-record-map-engine-validation.json), [whole-source selection](results/compiler-record-view-whole-source-check.json).

A separate actual 100-post [observer](results/compiler-record-view-observer.json) confirms each of four original/decoded/restored forms executes 454 native projections at 107 and 454 native Map reads at 108, with zero ordinary-kernel fallbacks, exact 500 indices, unchanged aliases and cleanup. This is a checked primitive path; it does not inline the complete Map algorithm into the generated loop. Negative tests reject multiple reads, public Map escape and mutation; replacing the exact same canonical Record with a fresh arena generation is rejected before reading.

The [500-post allocation diagnostic](results/runtime-gap-diagnosis/record-view-v1/receipt.json) counts 307,510 requests/67,613,511 requested bytes for unchanged source, versus 2,983,949/420,628,837 at the IR151 integration checkpoint. ## Comparison boundary

The upstream Rust timer excludes JSON reading/parsing and writing. It includes string indexing, scoring, top-five selection, and construction of the output records; its index and counters remain alive until after the timer. The Mech timer includes native `evaluate_into`, its internal temporary/retirement cleanup, exporting its indices, and constructing the same output records in the host. It excludes JSON IO, input preparation/admission, object restoration, and post-evaluation destruction of outputs/inputs. Input preparation flattens parsed post tags into strings and offsets, including tag-string clones, before immutable native admission. Reports separately record this whole preparation/admission interval and processing plus admission; newer summaries also give the combined multiple of Rust. The native compile/restore field starts after bytecode/frontend preparation and catalog construction; external wall time includes full startup. Neither implementation caches related-post computations between samples.

The Mech source uses a string-to-number map and a flat CSR posting index because the retained frontend rejects a map whose values are dynamically sized posting vectors. String-to-number lookup, allocation, and CSR construction are inside the Mech timer. `rust-csr.rs` is a secondary representation control with the same broad arrangement, u64 posting indices and u8 counters. It uses Rust's default `HashMap` hasher; the unchanged upstream implementation uses `hashbrown`. The original Rust program remains the primary baseline.

The adapter and both Rust implementations use Rust's system allocator. The retained linker template includes the DEFLATE experiment's allocator object, but this adapter does not install that experiment's custom allocator. Mech uses the DEFLATE experiment's `NoLimits` budget policy: configurable limits are maximal, and accounting/admission paths remain. This does not make resource-work counts hardware instruction counts or remove checked indexing/error paths.
