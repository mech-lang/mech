# v0.4 endgame boundary

This document freezes the qualified starting point for the v0.4 endgame. It is
a phase handoff, not a migration ledger or an authorization system.

## Validated R0 base

- Base commit: `9b6c68c47321d51233c8e2c93498cdf07d617963`.
- Source branch at qualification: `integration/value-executor-v0.4`.
- Full CI: [run 33352846650](https://github.com/mech-lang/mech/actions/runs/33352846650),
  dispatched with `release_channel=stable` and
  `validation_ref=9b6c68c47321d51233c8e2c93498cdf07d617963`.
- Result: all 77 jobs passed against the exact validation ref.
- Continuing integration branch: `integration/v0.4`, created at the same
  qualified commit and protected by the normal PR gate.

The root package version at this boundary is `0.3.6`. It remains `0.3.6` until
R7 qualifies `0.4.0`.

## Endgame phases

| Phase | Scope | Stop rule |
| --- | --- | --- |
| R1 — Canonical contract and compatibility closure | Remove opaque operation contracts, semantic implementation-identity fallbacks, migration-only compiler adapters, the old resident request bridge, half-supported operations, ineffective contract metadata, and the unresolved `no_std` product claim. | Do not begin R2 until every executable operation has a complete semantic contract; all specified compatibility fallbacks and old resident conversions are gone; advertised operations cannot reach `todo!()`; product documentation is truthful; and Full CI passes on the immutable R1 head. |
| R2 — Type–memory boundary | Define the semantic type/storage boundary, logical identity, ownership, publication capability, and accounting contracts consumed by later phases. | Stop before inference or allocator implementation if any type rule still depends on physical storage identity or an unspecified ownership rule. |
| R3 — Type inference, classes, and conversions | Implement inference, type classes, conversion selection, and diagnostics on the R2 boundary. | Do not cut over while any accepted program depends on ambiguous class resolution, implicit lossy conversion, or storage-backed type identity. |
| R4 — Type-system cutover | Make the new solver authoritative and retire the semantic-authority role of `FunctionValueRepresentation`, `FunctionRuntimeType`, and exact Rust matrix storage classes. | Do not begin memory planning until source, bytecode, native, and resident paths agree on inferred schemas and the transitional representations are execution details only. |
| R5 — Memory planner | Derive layouts, lifetimes, alias plans, resource budgets, and allocation requirements from canonical contracts. | Do not change runtime backing until plans are deterministic, validated before allocation, and cover rollback/publication lifetimes. |
| R6 — Memory runtime cutover | Implement planned allocation, cell backing, accounting, transaction storage, and resident publication behind canonical APIs. | Do not begin release work while public behavior exposes physical identity, memory limits are advisory, or rollback/publication can escape the planned storage contract. |
| R7 — Release qualification | Reconcile features, packages, documentation, platforms, artifacts, and versioning; qualify `0.4.0`. | Do not bump the package or release while any advertised profile lacks an exact owned gate or any preserved compatibility contract has changed without versioning. |

No additional cleanup phase is inserted between R0 and R1.

## R1 closure

R1 makes declared operation semantics mandatory for executable artifacts and
removes implementation-name recovery as an alternate semantic authority. The
resident write API now has one canonical provider request carrying effect and
idempotency identity. Assignment and set runtime validators are explicit
declaration data, set operations and table joins carry complete semantic
contracts, and unavailable operation surfaces were removed consistently.
The parser/container conversion helpers in `src/engine/src/artifact/ir.rs`
remain the canonical structured source-IR boundary; the R1 audit found no
heterogeneous runtime container acting as an alternate semantic authority.
The bytecode-v1 corpus and fresh-process determinism generator remain in place,
but generation now uses the canonical semantic artifact path rather than a
frozen implementation-identity projection.

The advertised root `no_std` profile builds under the pinned toolchain and is
run exactly by Full CI. `scripts/check-r1-compatibility-closure.py` permanently
forbids the retired compatibility names, paths, implementation namespaces,
compiler placeholders, and product claims. R1 merges only after Full CI passes
on its immutable head.

## Release blockers

- The R2 boundary has not yet separated semantic identity from physical
  storage identity.
- The R3 solver and conversion policy are not authoritative.
- Transitional runtime representations remain semantic authorities until R4.
- Memory layout and lifetime plans are not complete until R5.
- Memory accounting and transaction backing are not cut over until R6.
- Feature, documentation, packaging, and platform claims are not release
  qualified until R7.
- The root package must not be changed from `0.3.6` before R7.

## Non-goals

R0 changes documentation and archival placement only. It does not change
`KindExpr`, `KindScheme`, `SchemaBody`, `Value`, `ValueCell`, `CellBinding`,
`FunctionInvocation`, `FunctionValueRepresentation`, operation contracts,
artifact structures, runtime behavior, memory backing, resident execution,
bytecode-v1, canonical encoding, native linkage, dynamic-module ABI, Cargo
features, or the package version.

R1 does not redesign inference, conversions, `Number<T>`, memory layouts,
allocation handles, `Ref<T>` backing, cell allocation, snapshot storage,
`FunctionValueRepresentation`, `FunctionRuntimeType`, or exact Rust matrix
storage classes. Those belong to R2–R6. R1 also does not version or remove the
preserved compatibility contracts below.

## Preserved compatibility contracts

The following contracts remain until an explicitly versioned successor exists:

- bytecode-v1 format;
- canonical encoding v1;
- stable operation IDs as lookup keys;
- native linkage names;
- dynamic-module ABI v1;
- program artifact versioning.

Stable IDs identify declarations; they do not replace the semantics carried by
those declarations.
